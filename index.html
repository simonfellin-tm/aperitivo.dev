Spec & Design in. Working device out.

The factory compiles device software to a WebAssembly container that doesn't care which hardware it's on. That gives agents a closed loop: build, run, check against the spec, fix, repeat. All of it happens before anything is flashed to a board.

  1. 1
    Write the specRequirements, use cases and the signals your hardware exposes. Bring the PDF specs you already have. The spec stays the source of truth.
  2. 2
    Agents build itAI agents write the screens, logic and hardware bindings with full context of the embedded stack and your spec.
  3. 3
    Verify in the twinThe build runs in a browser twin. Agents test it against every requirement, and your team clicks through the real device on day one.
  4. 4
    Ship to the deviceDrop the unchanged container onto the dev board, then into production.

What's inside the factory.

A general coding agent knows a bit about everything. The factory gives it what it needs to ship a real device: the right stack, the right context, and a way to prove the result works.

stack/A proven embedded stackA real-time OS for the hardware, a graphics layer for the screen and a WebAssembly runtime for a safe app layer, chosen and wired together for you.
context/Context agents can useAPIs, patterns and constraints of the stack, packaged so agents build the way an experienced embedded team would.
spec/The spec as the mapStart from the whole product and zoom in. Every requirement is traceable to the code and the tests that cover it.
twin/A twin to test againstThe real build, running in a browser with simulated signals, so agents and people can check behaviour without hardware.

One clean line between software and hardware.

The factory builds the app container. You own the C connectors and drivers. In between sits a standard schema of named values, the pipe. Agents build against it, and it's the reason the twin behaves exactly like the device.

Built by the factory App container Screens and logic compiled to WebAssembly and running sandboxed on the device. Generated, tested and updated without touching your firmware.

Why WebAssembly on the device?

We started experimenting with WebAssembly architectures in 2024. Drivers stayed in C, and everything on screen ran in a WebAssembly runtime, because a screen should never be able to crash the machine. It also turned out to be exactly what AI agents need: a safe box they can build, run and test on their own.

Crash-safeThe app runs sandboxed. If it fails, the drivers keep running.
Safe for AI-written codeThe runtime manages memory, so generated code can't reach anything it shouldn't.
Hardware-agnosticOne binary for browser, board and product, across chip families.
Independent updatesShip a new app container without reflashing or retesting your drivers.
